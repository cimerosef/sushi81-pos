## 3. Authoritative storage semantics

The receipt identity is **business configuration**, not per-device printer configuration.

It must be stored durably in the authoritative SQLite business lineage so that every valid authoritative or read-only copy produced by handoff/recovery prints the same current approved identity.

Implementation may represent this as additional `BusinessSettings` fields or a tightly scoped singleton receipt-identity settings record/table, whichever is simpler and safer, provided that:

- there is one authoritative current identity block per business lineage;
- values are included in SQLite-safe handoff/recovery because they are part of the business database;
- normal M06/M07 write-authority rules apply to editing these values;
- non-authoritative devices may read/use the locally available committed identity for printing but may not edit it;
- printer queue names remain separate local technical configuration and are never moved into this business identity block;
- migration is additive and must preserve existing business data.

The initially migrated/default identity values are exactly the values in section 2.

## 4. Kitchen ticket visual target — owner-selected page 1

The kitchen ticket should preserve the compact thermal-ticket appearance of page 1.

The primary composition is:

1. centered prominent heading equivalent to `*** CUISINE ***`;
2. `Cmd : <order reference>`;
3. `Heure : <original creation/confirmation time>`;
4. first dashed separator;
5. a compact customer/order-information block;
6. second dashed separator;
7. ordered product lines in persisted order;
8. final dashed separator;
9. prominent `TOTAL : <amount> EUR`.

### 4.1 Customer/order information between the two upper separators

As explicitly requested by the owner, customer/order details such as telephone and remarks belong **between the two upper dashed separators**, not mixed into the product list.

That information block must use only committed fields that actually exist and may include, when applicable:

- `Retrait` / `Livraison`;
- planned fulfilment date/time;
- telephone;
- delivery address;
- full order comment/operational remarks.

Blank optional values are omitted rather than printed as empty pseudo-data.

For a future order, the structured planned fulfilment date/time must be made especially prominent in this upper information area (or immediately adjacent to it) so the ticket cannot reasonably be mistaken for a same-day order.

### 4.2 Product lines

The owner reference uses compact lines such as:

`1x P1 Poke Bowl Saumon`

M08 therefore keeps the approved `quantity + code + name` operational line recognizable in that form. Structured options/custom adjustments are printed immediately below/visually attached to their parent line, with indentation or another equally clear compact treatment.

Kitchen output does not add payment composition merely because payment data exists.

## 5. Customer ticket visual target — owner-selected page 2

The customer ticket should follow the overall Hiboutik receipt structure and density shown on page 2, without falsely presenting the document as generated by Hiboutik.

The primary composition is:

1. centered Sushi 81 identity block;
2. centered ticket/order reference and original date/time;
3. dashed separator;
4. compact customer/order information block when applicable;
5. dashed separator;
6. item detail rows;
7. dashed separator;
8. HT/VAT summary region;
9. dashed separator;
10. visually prominent final `Total` / `EUR <amount>` line;
11. payment/customer-information region where applicable;
12. a small technical footer may identify `Sushi81 POS` if useful, but it must not copy Hiboutik branding, version text, marketing text or website attribution.

### 5.1 Customer information adaptation

The reference page contains a customer name/address because that Hiboutik sale has those values. Current Sushi81 POS V1 deliberately has no Customer master and no ordinary customer-name field.

M08 therefore must **not invent a customer name field merely to imitate the sample**.

Use existing committed order information only, including telephone and delivery address when present. The customer-ticket styling may reserve the same visual block even when fewer fields exist.

### 5.2 Item/VAT/total presentation

The customer ticket should preserve the reference's dense receipt-table feel:

- quantity + product/code/description;
- readable saved price information;
- deterministic wrapping rather than clipping;
- HT/VAT summary derived only from persisted tax snapshots;
- authoritative TTC total visually much more prominent than surrounding rows.

`Total HT` may be derived from persisted `OrderTaxBreakdown` values as the sum of each persisted TTC bucket minus its persisted included-VAT amount. Per-rate HT bases may be shown the same way. M08 must not recompute historical VAT from current Catalogue/current VAT rules.

The sample's letter tax markers (`A`, `B`, etc.) are not themselves mandatory business data. Implementation may omit them unless a deterministic mapping materially improves the visual match.

Payment display uses the latest committed cumulative CB/Espèce values according to the existing printing specification.

## 6. Font / thermal-printer appearance

The owner's preference is to match the current Hiboutik ticket typeface as closely as practical.

The owner-supplied PDF is an image/scan and does not contain an extractable named font family. Hiboutik's own support documentation states that receipt printing normally uses the thermal printer's built-in fonts; the default receipt uses the smallest printer font, and Hiboutik exposes `<hibou_use_font_a>` to select printer **Font A**. The exact glyph appearance therefore depends on the printer model rather than on one portable Windows font file.

M08 visual rule:

- target the same narrow, monospaced thermal-receipt appearance and density as page 2;
- where the configured Windows printer driver exposes a stable printer-resident equivalent usable through the approved Windows spooler boundary, prefer it;
- otherwise use the closest reliable Windows/driver monospaced rendering and calibrate size/line spacing/character density against the owner reference during manual acceptance;
- do **not** introduce raw ESC/POS solely to chase an exact font match, because the approved V1 architecture uses standard Windows printing as the primary integration;
- if real-hardware acceptance later proves that standard Windows printing cannot reach an acceptable visual result, that becomes concrete evidence for the architecture's already-allowed later printer-specific adapter decision.

Exact font-family identity is therefore not an M08 authorization blocker; **visual similarity/readability on the actual printer is an owner-acceptance criterion**.

## 7. Reprint/cancellation markings

The owner-selected layouts do not supersede existing Approved safety markings:

- kitchen explicit reprint: `RÉIMPRESSION`;
- customer explicit reprint: `DUPLICATA`;
- any Cancelled-order document: prominent `ANNULÉ`;
- cancelled reprint: cancellation and reprint markings both remain visible.

These markings may alter spacing from the reference layout when necessary for safety.
