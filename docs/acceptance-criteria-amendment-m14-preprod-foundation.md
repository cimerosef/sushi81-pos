# Acceptance criteria amendment — M14 PreProd foundation

**Status:** Approved
**Date:** 2026-09-27
**Milestone:** M14

This amendment adds acceptance requirements for the permanent PreProd runtime and immutable candidate-to-production promotion flow.

## A. Deployment identity and local storage

1. `prod` and `preprod` are the only accepted official deployment profiles.
2. Production continues to use `%LOCALAPPDATA%\Sushi81 POS`.
3. PreProd uses `%LOCALAPPDATA%\Sushi81 POS PREPROD`.
4. Data, Config, Recovery, Archive, Cache, Logs and Temp are fully isolated.
5. Unknown/malformed/contradictory profile evidence fails closed before business database or authority initialization.
6. A PreProd process must never open production `live.db` or authority/config state as its writable runtime state, and vice versa.

## B. Installer coexistence

1. Production and PreProd use distinct stable Inno Setup AppIds.
2. Production and PreProd use distinct binary install directories, shortcuts and uninstall identities.
3. Both may be installed on the same Windows user profile.
4. Repair/reinstall/uninstall of one environment does not remove or mutate the other environment's durable data.
5. Durable application data remains outside installer-managed binary directories.

## C. Permanent PreProd marking

1. PreProd window/application identity is explicit.
2. Major operational UI visibly states that the environment is PreProd/test data.
3. Kitchen prints, customer prints and reprints include a clear PreProd marker.
4. Default Gestion export filenames include `PREPROD_`.
5. Marking does not change business calculations, export column/schema semantics or stored operator-entered business data.

## D. Initial production seed

1. Initial seed is allowed only from a pristine PreProd environment and only while no PreProd pairing/handoff/business test lineage has been established.
2. Source production application must not be actively writing during seed.
3. Production `live.db` is read-only to the seed operation.
4. A SQLite-safe snapshot/backup and integrity validation are required; raw live-file copy is prohibited.
5. Staging/validation failure leaves existing PreProd durable state unchanged.
6. Database migration failure leaves the prior/pre-seed PreProd state safe and retryable.
7. Production authority/device/lineage/pairing/remote config/credentials are never copied.
8. Canonical production annual Archive databases are not copied by M14.
9. Real production database bytes never enter the source repository, Git history, source-repository Release, Actions artifact, tests or samples.

## E. Runtime authority and remote isolation

1. PreProd establishes an independent lineage and independent device IDs.
2. Existing target-directed GitHub handoff semantics are reused unchanged inside PreProd.
3. PreProd GitHub handoff repository must differ from production.
4. PreProd Credential Manager target must differ from production.
5. PreProd OneDrive root must differ from production and neither root may contain the other.
6. Configuration collision is blocked before persistence.
7. PreProd normal handoff discovers/uploads/downloads only through PreProd runtime configuration.
8. PreProd DR checkpoints and System metadata use only the PreProd OneDrive root.
9. Production authority state, generation and runtime transport artifacts remain unchanged by PreProd pairing/handoff acceptance tests.

## F. One-publish immutable payload

1. A candidate application payload is generated by one `dotnet publish` execution.
2. CI produces a payload manifest containing source SHA and SHA-256 for all application payload files.
3. PreProd installer packaging uses that payload.
4. Accepted candidate promotion downloads/verifies that exact payload.
5. Production promotion must not execute `dotnet publish`.
6. Production packaged application files must match the accepted candidate payload manifest byte-for-byte.
7. Any hash mismatch, missing manifest, wrong source/candidate identity or attempted rebuild fails promotion closed.

## G. GitHub candidate/release evidence

Each owner-testable candidate must have durable GitHub evidence including at least:

- candidate ID;
- source SHA;
- exact-head CI run;
- product version;
- payload manifest/SHA-256;
- PreProd installer SHA-256;
- immutable downloadable candidate asset.

Final production packaging evidence additionally records:

- accepted candidate ID/tag;
- accepted source SHA;
- accepted payload SHA-256;
- production packaging run ID;
- production installer SHA-256.

## H. Owner manual acceptance

On the two real Windows computers, owner acceptance must prove at least:

1. production and PreProd coexist;
2. PreProd is visually unmistakable;
3. one initial seed from current production data succeeds without importing production authority identity;
4. representative catalogue/settings/order/Gestion data are present;
5. independent PreProd OneDrive/GitHub/Credential configuration succeeds;
6. PREPROD-A and PREPROD-B form an independent paired system;
7. at least one target-directed A→B PreProd authority handoff succeeds;
8. production remains operationally isolated and unchanged;
9. PreProd print/export marking is visible;
10. payload-equivalence evidence proves accepted PreProd payload equals the payload packaged for production promotion.

Owner acceptance does not repeat full M01–M13 business regression.

## I. Completion gate

M14 is not Passed unless:

- exact-head CI is green;
- Release build is 0 warnings / 0 errors;
- tests are 0 failed / 0 unexpected skipped;
- all required automated isolation/promotion tests pass;
- owner manual acceptance passes;
- docs/status are reconciled;
- M12 deferred real populated-archive verification remains explicitly deferred and is not relabelled Passed.
